## 编号约定

- 文件名：`NNNN-<kebab-case-英文短标题>.md`，编号从 `0001` 起，四位零填充，不复用、不跳号。
- 一个决定一份文件。若新决定推翻旧的，**不删除旧文件**：在新文件顶部写 `取代：ADR-NNNN`，同时把旧文件的状态改为 `被 ADR-NNNN 取代`，并在本索引更新两行。
- 与既有 ADR 冲突时明确摆出来，不要悄悄覆盖（`docs/agents/domain.md`）。

## 正文结构

每份 ADR 至少包含这四节，顺序固定：

- **决定** —— 定了什么，用陈述句写；一条决定只讲一件事。
- **背景** —— 定这条决定时的事实与证据。可以引用代码位置、提交数、审查报告章节。写事实，不写修辞。
- **被否的替代方案** —— 认真考虑过的其它走法，以及它们各自为什么不行。这一节是 ADR 存在的主要理由：没有它，后人只会重新提一遍。
- **后果** —— 接受这条决定换来了什么、付出了什么代价、管不到哪些地方，以及什么情况下应当回来重新审视。

标题与正文用中文，全角标点，中英文之间留一个空格；代码标识符、文件名、英文技术名词保留原样（`AGENTS.md`）。

## 与其它文档的分工

- **ADR**（本目录）—— 为什么这样定，一个决定一份，接受后不再改内容。
- `docs/legacy/architecture-complexity-review.md` —— 一次只读审视的盘点结果，问题是「哪里复杂度高」。
- `docs/legacy/architecture-refactoring-plan.md` —— 分阶段实施方案与推进状态，问题是「怎么改、改到哪一步了」。
- `CONTEXT.md` —— 领域词的唯一定义处；ADR 里用到词表外的概念，先补表再落笔。
