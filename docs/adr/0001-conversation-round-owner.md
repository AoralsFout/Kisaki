# ADR-0001：对话回合的 Owner 是 ConversationSession，不是 Pinia store

- 状态：已接受
- 日期：2026-09-11
- 关联：spec #13（给对话回合一个 store 之外的归属）；实施工单 #14–#22；`docs/architecture-complexity-review.md` §1、§2、总体优先级；`docs/architecture-refactoring-plan.md` 目标原则、验收结果

## 决定

**一个业务概念只有一个可变状态 Owner。** 对话回合这个业务概念的可变状态 Owner 是 `ConversationSession`（application 层，无框架依赖）；Pinia store 只做界面投影与命令转发。

具体含义：

- `ConversationSession` 拥有一次对话回合的全部编排：守卫、用户消息事务、检查点、工具清单装配、回合循环、后台语音准备、say 合成、终态分类与遥测。回合级的可变状态只存在于它内部。
- 其它模块只有两种接触方式：读它产出的投影，或向它发命令。没有第三种。
- 对外只有一条缝：`send` / `cancel` / `projection` / `subscribe`（收口时按需增补了只读的 `subscribeMessages`，见下）。各端口（模型客户端、翻译、角色人设来源、模型上下文、会话事实、工具执行、语音播放入口、时钟与 id、在线状态探测、界面文案、工具清单）是实现专属的内部缝。
- Pinia store 退化为两件事：订阅投影、写入自己的响应式状态；把用户动作转发为 `send` / `cancel`。
- 纯界面开关（输入框开合、气泡显隐）不进入投影，仍由 store 自己持有——它们不是回合业务概念的一部分。

### 收口时补的一条出口：`subscribeMessages`

界面消息列表（store 的 `messages`）不在投影里——它是展示层自有状态，决定见 #14。但它的每条 id 必须与会话事实一致：语音回填按 id 修订，回档按 id 寻址。因此 `ConversationSession` 另开一条**只讲事实**的订阅 `subscribeMessages`，发出「哪条消息以什么内容落库了」（用户消息已接收、助手消息已提交 / 已修订）。

这是投影之外唯一的增补，且不违反上面两条：**它不是第三种接触方式**——订阅者只读事实、不回写，回合状态的所有权没有转移。术语表已收录该出口（`AGENTS.md` 的「消息事实出口」）。

这不是一条新原则。`docs/architecture-refactoring-plan.md` 的「目标原则」第一条就是它，阶段 1–5 已经按它改造了会话聚合、角色运行时、工具执行与 TTS 管道。**对话回合是目前唯一尚未遵守它的部分**，本 ADR 记录的就是收口这一步。

## 背景

### 事实

> 本节记录**重构前**的状态，行号以分叉点 `master`（`d561547`）为准。这些坐标随本次改动失效——现在按内容检索，不要按行号定位。

- `src/stores/chat.ts` 是全仓库改动最频繁的文件：52 次提交（`git log --follow -- src/stores/chat.ts | wc -l`）。该切片的最高频修改面，同时是它最大的未测表面。
- `sendMessage` 曾是 641 行的隐式状态机：11 个被嵌套闭包共享改写的可变绑定（`failed`、`modelCallCount`、`toolCallCount`、`toolFailureCount`、`turnsUsed`、`fallbackUsed`、`ttsRequested`、`deliveredFinal`、`terminalReason`、`checkpointId`、`wasCancelled`），散布在 5 个嵌套闭包里；函数体内现场读取 18 处环境依赖，涵盖配置加载、模型调用、翻译、角色 store、在线状态探测、id 与时间生成六类，外加一个模块级 TTS 编排器单例。
- 协作者在 store 的函数体里被构造，在订阅回调里互相接线。端口的注释写着「由组合根注入」，实际注入点在 store 的函数体里；组合根的模块说明声称「谁被安装、安装了几次可以从这一处读出来」，但对话与会话切片的全部协作者都不在那里构造。
- 无法在不启动一整套环境的前提下测试回合：现有测试必须整模块 mock 掉 AI 模块、手工构造一个 11 方法的 `ChatSessionPort` 字面量、并调用 `setActivePinia`。测试面是 store 的宽接口，不是行为接口。
- 取消语义有两个来源：一条路径手工合成一个 `AbortError` 扔给调用方，另一条读回合计状态机已经记录的「已取消」。两者不一致时，界面的反馈与真实状态脱节。
- 「后台语音不得越过自己的回合」这条约束由 5 个调用点各自记得调用同一个取消函数来维持（`cancelBackgroundVoicePreparation()`，调用点 `src/stores/chat.ts:588`、`:1220`、`:1274`、`:1304`、`:1323`）。漏掉任何一处，用户就可能听到上一轮或上一个会话的语音。这类「记得调用」的约束没有任何类型或模块边界来强制。更糟的是那个函数持有的其实是一整个回合句柄（`chat.ts:774` 把 `conversationRun` 交了出去），所以「取消语音」与「取消回合」在今天共用同一个动作——约束不但靠人工维持，连它取消的是什么都不是它自己的名字所说的那样。

### 为什么这不是「再拆小一点」的问题

审查报告的结论是：最优先的动作不是继续拆小 ChatStore，而是先建立 Conversation Run 与 Session Aggregate，**否则其它局部重构仍会被 ChatStore 的总协调职责重新吸收**（`docs/architecture-complexity-review.md` 总体优先级）。只要 store 仍拥有全部协作者并负责把它们接起来，「总协调」这一职责就还在它身上；抽取出来的东西最终会重新长回它那里。

## 被否的替代方案

### (a) 把编排留在 store

若记录 ADR，最直接的反面选项就是维持现状：编排继续由 `src/stores/chat.ts` 承担，界面投影与业务编排共处一个 Pinia store。否掉它的理由：

- **总协调职责本身就是复杂度的来源。** 它不是「一个碰巧很大的文件」，而是一个吸收点：任何局部抽取进入它之后都会被重新编排回去（见 (b) 的实测结果）。
- **可变状态只有一个 Owner 是既有已声明的原则。** 对话回合不遵守它，是这份原则唯一的例外；保留例外等于取消原则。
- **Owner 的身份必须与宿主解耦。** store 是 Vue 响应式对象，编排状态与 UI 响应式状态共享同一个身份，「界面能看到什么」与「编排内部有什么」无法分离。回合逻辑被绑在 Pinia 上，无法在其它宿主下运行或验证。
- **测试面被宿主撑宽。** 上文的 `setActivePinia` + 11 方法端口字面量 + 整模块 mock 就是这一点的直接代价。

### (b) 只抽纯的部分，不抽编排（上一轮重构方案的做法）

上一轮重构（`docs/architecture-refactoring-plan.md` 阶段 4）把回合里所有**纯**的部分抽走了：流协议解码移入 `ModelStreamDecoder`、单轮模型返回解释移入 `ModelTurnInterpreter`、原生与文本工具调用统一为 `ToolCallBatch`、回合迭代与上限移入 `ConversationCoordinator` 的显式状态机。这些模块都建成了，也都被复用了，组件质量没有问题。

**它失败的地方在于编排没有跟着走。** 协作者仍由 store 自行组装、在订阅回调里互相接线，于是：

- `sendMessage` 从审查快照（`bf25675`）的 749 行减到 641 行（当时 `src/stores/chat.ts` 为 1,559 行，该函数位于 `:570`–`:1210`——本次收口后该文件为 592 行，函数已整体移出）。抽走的 108 行是纯计算；**编排连同它的 11 个可变绑定与 5 个嵌套闭包一行未动**。
- 方案的「过渡期边界」自述未收口：端口注释与实际注入点不符、组合根本应集中装配却读不出对话切片的协作者。
- 结论：**抽取的判据不是「这段逻辑是否纯粹」，而是「这个业务概念的可变状态 Owner 是否换了」。** 纯函数抽走了、Owner 没换，复杂度就没走。

这条教训决定了本次改动的形状：先换装配归属（复杂度审查候选 2），再建回合深模块（候选 1）。**候选 2 是候选 1 的前置条件**，两者必须作为一次改动执行。

## 后果

### 正面

- **缺装配显式失败，而不是静默空转。** `ConversationSession` 构造时要求全部端口就位，缺失即抛错并给出明确信息；静默成功的空实现端口被删除。用户可感知的失败从「回复正常显示、切换会话后消失」变成「启动即报错」——这一点比前者诚实得多。
- **取消只有一个真相来源。** 回合计状态机记录的终态是唯一依据，手工合成的 `AbortError` 路径删除。界面行为（气泡是否停、是否提示失败）不再有第二个可能与真实状态脱节的来源。
- **后台语音边界由模块边界强制。** 语音订阅 `ConversationSession` 的已提交事件，回合收口即边界关闭。新增调用点时不再需要「记得补一次取消」——漏掉不再是一个可能的错误，因为它不是一个可选项。
- **回合在一条缝上可测。** 不需要 `setActivePinia`、不需要构造端口字面量、不需要 mock 整个 AI 模块。「后台语音准备是否被取消」成为可直接观察的投影状态，而不是从日志缓冲区里推断。
- **组合根成为唯一装配点。** 新增一种注入依赖只需改一处声明，不必在函数体里多读一个环境全局；「谁被安装、安装了几次」重新可以从一处读出来。
- **回合实现可整体替换而不改变对外语义。** 今后的重构能在既有测试的保护下进行。

### 代价与负面

- **多了一层间接。** store 侧的命令转发与投影订阅是一次额外的 hop，读代码时需要在 store 与 application 层之间跳一次。
- **投影形状要手工维护。** `ConversationSession` 不再能随手借用 Pinia 的响应式便利，`ConversationProjection` 的字段与语义必须显式定义并随回合状态演进。
- **迁移期两个实现并存（已收口）。** 按 spec 的实施顺序，旧回合实现与 `ConversationSession` 曾短暂共存、由组合根选择——这是过渡成本，不是终态。收口工单已删除旧实现、临时适配器与静默空转的端口回落，代码库只剩一个实现；同时退休了只服务于迁移期的再导出与注入函数。
- **新增术语必须先入表。** `ConversationSession`、投影形状、消息事实出口等词原先不在 `AGENTS.md` 术语表内，落笔前先补进表里（`docs/agents/domain.md` 的规矩）——本次已随各工单一并补齐。

### 这条决定管不到的地方

- 会话持久化 schema（v2 timeline）与文件格式不变，无需数据迁移。
- 角色外观、检查点、回滚的语义不变。
- 工具批准的三类生命周期（文件 / 命令 / 截图）不变。
- 纯界面开关（输入框开合、气泡显隐）仍归 store；它们不进入投影。
- 用户可见行为不变——**唯一一处例外**是切换角色：今天它只取消后台语音与播放，不终止回合也不收气泡（`chatContext` 已被重建、进行中的回合仍继续往气泡里写）；本次改为干净地终止回合，依据是 spec user story 6 与勘察笔记 §N 把角色切换列为取消触发之一。这条例外必须在 PR 描述里单列。同一条边界也覆盖了原第 6 条越界路径：`refreshModelContext`（AI 配置变更）此前从不取消后台语音，现在会。

### 什么时候应当回来重新审视

- 若 `ConversationSession` 开始持有纯界面状态，或反向 import Vue / Pinia / Tauri API（架构边界测试应当拦住后者），说明 Owner 边界正在被侵蚀。
- 若出现第二个「也想知道回合状态」的消费者，正确的动作是**扩展投影**，而不是把回合状态分发到第二个 Owner。
