# ADR-0003：工具协议契约归属 domain/tools

- 状态：已接受
- 日期：2026-09-22
- 关联：spec #25；实施工单 #60；ADR-0001；`CONTEXT.md` 的「工具契约」与「工具清单」

## 决定

工具协议契约归属于 `src/domain/tools/contracts.ts`。它只定义模型、回合编排和工具适配器之间传递的纯数据形状：工具定义、工具调用、工具结果、工具图片、工具输出，以及工具清单筛选所需的中立上下文投影。

具体工具实现的 `handler`、注册表和执行策略仍归 `src/agent`；它们可以依赖工具协议契约，但协议契约不得反向依赖 Agent 实现、应用编排、界面层或 Tauri。

模型可见工具清单只有一个装配入口：`assembleRoundToolList`。它先使用工具清单端口返回角色可见工具，再按既有语义把 `say` 放在末尾。清单的序列化测试固定工具名称、参数和顺序，修改这些字段必须显式更新契约测试。

## 背景

`src/agent/types.ts` 同时承载模型协议数据和具体工具实现接口。`ConversationSession`、工具执行协调器、模型上下文适配器、设置页检查器和 Agent 实现共同引用它，使应用层和基础设施层都被迫知道 Agent 类型文件的位置。

此外，模型工具定义由注册表顺序、角色渲染方式、能力快照、工作区授权和安全设置共同筛选，回合与设置页都依赖同一份装配函数。若只按名称分别断言，参数和顺序仍可能漂移，模型实际收到的协议就会在没有明显编译错误的情况下改变。

## 被否的替代方案

### 继续把共享契约放在 `src/agent/types.ts`

否决。`agent` 是工具实现边界，不是模型协议或回合编排的 Owner。继续把协议类型留在这里会维持应用层对实现模块的反向依赖，也会让下一步把授权上下文下沉到工具端口时继续沿用错误归属。

### 把契约放进 `src/application`

否决。工具实现和基础设施适配器也消费这些数据形状；把它们放到应用层会让中立协议反过来依赖回合编排，无法成为跨层共享的纯契约。

### 用多个调用方各自维护工具清单快照

否决。回合实际发送的清单与设置页展示的清单会再次分叉，工具名称、参数或顺序变化时无法由一个行为测试发现。

## 后果

正面影响：

- 应用层和基础设施层只依赖 `domain/tools` 的协议契约，不再依赖 Agent 类型实现文件。
- 工具实现仍可保留现有字段语义；实现行为类型归属 `src/agent/tool.ts`，不保留旧的契约兼容入口。
- 模型可见清单的名称、参数和顺序有单一装配入口与契约测试保护。

代价与边界：

- 契约仍使用当前协议兼容的 `Record<string, any>` 参数形状；本决定不引入完整 JSON Schema 类型系统。
- 角色数据与运行时能力通过工具清单上下文的中立投影传入；具体角色加载器和 Runtime 类型不进入 domain 契约。
- 本决定只收口类型归属与清单契约，不改变工具批准、工作区授权或角色能力行为；这些行为由后续 #61–#63 处理。
